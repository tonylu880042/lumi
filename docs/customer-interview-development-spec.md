# 客戶訪談導向開發規格

> 日期：2026-10-02
> 狀態：客戶需求對照已整理；已核准的後續修訂依 ADR-0021，未決契約不得當成已核准規則。
> 來源：owner 在本次對話提供的完整客戶訪談；工作區原始逐字紀錄為 [0922 討論.txt](interviews/0922%20討論.txt)。
> 適用：SYSTEM_SPEC.md、architecture.md、ADR-0011／0017／0018／0019／0020／0021。

## 1. 目的與採用的前提

Lumi 要交付客戶描述的認識會員、進店迎賓、運動後離店鼓勵、量身面談提醒、
文案輪替及達標音效。以下前提來自已確認的對話與規格，不另推定產品規則：

- 訪談是產品場景與成果的依據；owner 後續明確確認的修改優先於較早的訪談草案。
- ADR-0021 已定案：本週見面鼓勵採台北時間週一至週日，同日只算一次。
- ADR-0021 已定案：量身面談在日曆 1–10 日提醒，每會員每日最多一次，教練確認當月完成後停止。
- Owner 已選定第一版週次數與月 12 次里程碑的來源：「我們看到一次就算一次」。沿用已確認的同日最多一次；以 Lumi 觀察計次提供鼓勵與里程碑，不標成正式完成運動紀錄。離店服務仍須交付，不能只做進店鼓勵。
- Owner 於 2026-10-02 確認沿用連續三秒沒有可用臉部，但它只用來結束本次互動／重新待機。當天第一次紀錄建立至少 30 分鐘後，再次可靠辨識本人，就在會員仍在鏡頭前時播放離店鼓勵；不等三秒無臉，也不把持續在場滿 30 分鐘當成再次見面。不能宣稱已具備人體離場或完成運動偵測。
- 客戶不必回答例行迎賓／提醒；同意、稱呼與會員主動提問仍保留。
- Owner 於 2026-10-06 確認：當天首次迎賓報包含今天的本週次數，依第一次、第二次、第三次以上給鼓勵，取代舊歷史開場；首次已保存招呼後未滿 30 分鐘的每次新互動只說「又見面啦，加油喔」，不重報次數。滿 30 分鐘仍沿用離店鼓勵；招呼完成後才保存的規則不變。
- Realtime 按需啟動、一般播報改用錄音／TTS 是待評估的技術建議，尚未核准具體啟動 UX；不能直接撤掉現有口頭登錄流程。

| C2 第 1–4、6 點：運動後離店 | 當天第一次紀錄至少 30 分鐘後，再次可靠辨識本人時，開場播報一次本週 Lumi 觀察次數與鼓勵；未滿三次鼓勵繼續，已滿三次肯定並鼓勵維持；不要求回答「今天運動如何」 | Domain 資格、同意後的當前會員綁定、語音 context 與 Realtime 開場已接入；取代一般錄音迎賓且重連不重播，實機驗收待執行。三秒無可用臉只結束互動；一般道別或鏡頭無臉不自動新增一次。不能將觀察計數標為正式完成運動 |
| C3 第 5 點：今天完成第一次運動 | 依目前選定的觀察來源肯定來店；使用「完成運動」字句仍需相應證據與已核准語意 | 「第一次」指本週第一次、當日第一次或首次參與未明確；目前資料來源不能確認完成運動，不能將這句原文直接當固定錄音 |
| C4 第 7 點：每週輪替說法 | 同一有效情境可依週別輪替已確認的短文案；輪替不得改變資料、次數或提醒資格 | 現有錄音選擇有變化，但不是週別輪替。文案庫與輪替契約待確認；不固定只說同一句 |
| C5 第 8 點：達標音效 | 依 owner 選定的 Lumi 觀察計次，當月達到 12 次時使用特別音效；依既有決策，每會員每月最多一次 | 來源已選；月次數契約、播放／取消／更正、重啟去重待定。音效與文案肯定觀察到的持續來店，不宣稱正式完成 12 次運動。訪談泛稱的額外週音效門檻未定 |
| C6 第 9 點：量身面談 | 依最新修訂，日曆 1–10 日每天最多提醒一次，教練確認當月完成後停止；跨月不能沿用上月完成 | 教練入口、權限、會員綁定、同意、留存、更正、播放去重與日界待定。每月 1 日週日順延至首營業日的既有決策保留；營業日來源待定 |
| C7 第 1 點：週五／週六邀請 | 只有實際營業日與有效運動情境支持時才邀請特定日期來運動 | 門店日曆未接入，不能一律宣稱週五／週六可來 |
| C8 語音 Vale／Maple | 保留客戶的聲音偏好，實際試聽並確認迎賓、提醒、對話、道別一致性與響度 | 聲音來源／供應端支援尚待核對；目前使用 Marin 與既有音檔，不能只將偏好名稱寫入設定就視為支援 |
| C9 目前缺點：太過囉唆 | 一般訊息短、一次一個重點、例行提醒不追問；必要告知完整。真人試辦檢查文案與音檔，不能只靠 prompt assertions | 提示政策已有實作，07-goodbye 等既有音檔與真人接受度仍有待辦；不自行加入硬秒數截斷 |

每一列都要分別記錄「規格定案、程式實作、自動化驗證、實機驗收」狀態。
完成見面鼓勵或提示政策不能把 C2/C3/C5 標為完成；類別存在、安裝成功也不是客戶驗收。

## 4. 技術位置與風格

- Swift 6 package；iOS 17 以上 App。Domain 管日期、計數與選擇規則，不匯入 Apple 音訊／相機或網路框架。
- `Sources/LumiApplication/Ports` 與 `UseCases` 管資料來源契約、目前會員綁定及合法操作；coordinator 保持唯一 session owner。
- `Sources/LumiInfrastructure` 實作資料、音訊／TTS／Realtime 和相機 adapter。
- `Sources/LumiPresentation` 映射 UI 自有值；`Sources/LumiUI` 和 `App/LumiApp/Sources` 呈現會員／教練操作入口。
- 沿用明確命名、`Sendable` port、型別化錯誤與 async 邊界。例如既有 Application port：

```swift
public protocol MemberRepository: Sendable {
    func profile(for id: MemberID) async throws -> Member
    func weeklySummary(for id: MemberID) async throws -> ExerciseSummary
}
```

這是目前介面風格範例，並不把既有 `visitsThisWeek` 重新命名就當成新的完成運動契約。

## 5. 測試與命令

每個 production 行為先寫 failing test，確認預期原因後才實作，採 RED → GREEN → REFACTOR。
規則測試放 `Tests/LumiDomainTests`；身分／權限／去重及 Use Case 放
`Tests/LumiApplicationTests`；來源／保存／音訊契約放 `Tests/LumiInfrastructureTests`；
UI 映射與 App 組裝分別放 Presentation tests 與 `App/LumiAppTests`。

運動紀錄定案後至少涵蓋週 0／1／2／3／超過 3、月 11→12→13、跨日週月、
同日重複、撤回／延遲與故障；不完整資料不得被當成零次。提醒與播放還需涵蓋
1／10／11 日、同日限一次、教練確認、跨月、取消、重啟及下一位會員。

每次交付執行：

```sh
swift test
xcodebuild -project App/LumiApp.xcodeproj \
  -scheme LumiApp \
  -destination 'generic/platform=iOS Simulator' \
  CODE_SIGNING_ALLOWED=NO build
```

實機遵循 AGENTS.md，只用 `LumiApp-Live`／`Debug-Live`，安裝前核對
`CFBundleIdentifier == com.curves.lumi.live`。本文件不授權本輪部署。

## 6. 開發邊界

- 必須：每個變更對應 C0–C9 的客戶成果或其必要依賴；保留既有工作區變更；如實報告缺漏與驗證。
- 未決先確認：會影響 UX、資料、隱私、狀態、音訊啟動或驗收的規則，依 AGENTS.md 問 owner；不重問已定案的 1–10 日／每日一次／教練確認。
- 禁止：見面冒充完成運動、模擬 fixture 冒充真實紀錄、LLM 自選會員 ID／日期或控制馬達、UI 直接存取硬體／網路、未同意擴張資料用途。

受未決契約阻擋的功能保留為未完成。已核准且相依已滿足的工作可繼續；實作計畫須
以本表、roadmap 與後續確認的契約為依據，不能用技術選型縮減客戶要求的離店服務。
